# Commits

Each commit does one logical change, so `git log --oneline <base>..HEAD` reads as the story of the change and a reviewer can go commit by commit. Splitting rewrites history, not code. The final code stays identical and only the commit hashes change.

## When to rewrite

| Branch state | What to do |
|--------------|------------|
| Not pushed, or pushed with no PR yet | Rewrite freely |
| PR open with no review or comment yet, draft included | Rewrite, then push with `--force-with-lease` |
| PR with reviews or comments | History is frozen. Add new commits on top and push normally |

## Steps

1. **Back up** under a name no earlier run used. Note the printed name and write it out in every later command where `<backup>` appears:

   ```bash
   bk="backup/<slug>-$(date +%Y%m%d%H%M%S)"; git branch "$bk" HEAD; echo "$bk"
   ```

2. **Read** `git log --oneline <base>..HEAD` and `git diff --stat <base> HEAD`. Spot unrelated files (regenerated by a dev server or build, lockfile churn, debug leftovers) and unrelated work (a drive-by fix, a dependency bump, a refactor the change does not need). Ask the user before leaving any of it out. Unrelated work they want kept moves to its own branch, created from `<backup>`, for a separate PR.
3. **Plan the groups.** One logical change per commit, each building on its own. Foundations first (shared types, then back end, then front end, then docs), tests in the commit of the code they cover. Messages follow the repository's format from step 1 of the skill, or Conventional Commits (`type(scope): subject`) when it has none.
4. **Rewrite** with the smallest tool that fits:
   - **Fold fixup commits.** Fixes made while running the checks or capturing evidence were committed with `git commit --fixup=<target-sha>`. `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <base>` moves each one next to its target and folds it in. With history frozen, leave them as they are. A conflict means a later commit touches the same lines. Recover as in step 5, then regroup instead.
   - **Regroup existing commits.** Run `git reset --soft <base> && git reset`, then for each group `git add <paths> && git commit -m "<message>"`. Files left out on purpose stay in the working tree. Once the groups are committed, set them aside with `git stash push -u -m "left out of <slug>"` so later rebases run on a clean tree, and name the stash in the report.
   - **Split one file across two commits.** Run `git diff <base> -- <file> > /tmp/pr-<slug>/split.patch`, keep only the first group's hunks in it, stage them with `git apply --cached --recount /tmp/pr-<slug>/split.patch`, commit, then `git add <file>` for the next group.
5. **Recover** from a conflict or a failed command with `git rebase --abort` when a rebase is in progress, then `git reset --hard <backup>`, and redo the plan.
6. **Check the result:**
   - `git diff --stat <backup> HEAD` is empty, or lists only the files the user agreed to leave out. Anything else means code was lost or added. Recover as in step 5.
   - `git rebase --exec "<fast check>" <base>` passes on every commit, with the typecheck or build of the changed packages. When that is too slow, check the last commit and say so in the report. When a commit fails, `git rebase --abort` and fix the plan.
7. **Keep `<backup>`** until the PR merges. The final report names it so the user can delete it with `git branch -D`.

## Review fixes

After review starts, each fix is a new commit on top, named after what it fixes. When the repository squashes on merge, the squash cleans the history. Otherwise, fold the fixes once the reviewers approve, and only with their agreement.
